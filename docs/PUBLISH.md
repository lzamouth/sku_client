# Publishing a version of the client

Internal document (SkunkCrafts). The guide for third-party developers is
[PUBLISHING.md](PUBLISHING.md), the user guide [USER_GUIDE.md](USER_GUIDE.md).

## Where

Everything is on the store CDN, the S3 bucket mounted at `/remote/s3/aerobask`
and served by `https://1228098873.rsc.cdn77.org/`, in its `updater/` folder:

1. **The client depot**, sub-folder `updater/depot/`, using the addon
   protocol: `skunkcrafts_updater.cfg`, whitelist, sizeslist, empty blacklist,
   `changelog.txt`, `readme.txt`, the guide, and the packages under their
   **versioned name** (`SkunkcraftsUpdater-4.0.0-linux.zip`, `sku-cli-4.0.0.zip`).
   The client derives the package name from the published version; that way
   a list served stale by the CDN can never point to a file of another
   version. Fixed names remain accepted as a fallback for old depots.
2. **`updater/`**: the five downloads under a fixed name,
   `SkunkcraftsUpdater-windows.zip`, `-windows-setup.exe`, `-macos.zip`,
   `-linux.zip`, `-x86_64.AppImage`, plus `sku-cli.zip`, `USER_GUIDE.html`,
   `USER_GUIDE.md`, and the developers' guide `PUBLISHING.html` and
   `PUBLISHING.md`. These are the permanent links of the download page; their
   content changes at every version, not their name. The list of links for
   the store page, `updater/urls to updater v4.txt`, therefore no longer needs
   to change at every version; the script does not touch it.

Two old addresses only serve to redirect, through a cfg whose `module`
announces `https://1228098873.rsc.cdn77.org/updater/depot`: the Bunny depot
`cdn.skunkcrafts.com/updater/skunkcrafts/sku_client` (clients up to beta7)
and `1228098873.rsc.cdn77.org/sku_client` (beta8). Clients follow; these
addresses can go once nobody queries them any more. An old client only
follows the move after a successful check at the old address, which reads
the cfg **and** the whitelist: keep both there. Since 4 October 2026 the
`sku_client/` folder holds only its cfg, lists, changelog, readme and guide;
its packages, like the fixed-name copies the depot used to keep for clients
up to beta7, have been removed.

## The sequence

```bash
./release.sh 4.0.0          # builds the three targets, produces dist/4.0.0/
docs/publish.sh 4.0.0       # publishes to the bucket and checks
```

`release.sh` requires `CHANGELOG.txt` to start with the version line, like
an aircraft changelog, and produces `dist/<version>/depot/` ready to
publish, including `USER_GUIDE.html` generated by `tools/md2html.py`.
`CHANGELOG.txt` is what clients show under "What's new": since 4.0.0 it
describes the published versions only, the history of the betas lives in
git.

`publish.sh` refuses to start if `dist/<version>/` is incomplete, if the
depot cfg does not carry the version or the S3 depot URL, or if the bucket
is not mounted. Then:

1. generates the depot's whitelist and sizeslist, writes the **locked** cfg
   to `updater/depot/`, copies the files, writes the **unlocked** cfg;
2. copies the fixed-name downloads and the guide to the root;
3. checks that the fixed URLs and the depot cfg answer 200 and that
   `sku client` sees the published version.

`docs/publish.sh <version> --dry-run` prints the actions without sending
anything.

The developers' guide changes between versions of the client: every
publication puts `docs/PUBLISHING.md` online as it is then, and
`docs/publish.sh --dev-guide` publishes it alone, HTML and Markdown,
without touching the depot.

## What the script does not do

- It deletes nothing in the bucket: the versioned packages of previous
  versions stay in `updater/depot/`, to purge by hand from time to time
  (nothing references them once the cfg has moved to the next version).
  Before deleting, check that `dist/<version>/` still holds an identical
  copy.
- It does not purge the CDN77 cache: fixed-name files and lists may be
  served stale for the duration of the cache. The versioned names of the
  depot make this harmless for clients; for the fixed links, a user may
  receive the previous version during that time.
- It does not push the git repository: pushing to the private GitHub mirror
  (`lzamouth/sku_client`) is done separately, by hand.
- It knows no secret: the bucket is mounted by s3fs with its own
  credentials.

## After publication

An earlier 4.0 client, started within the hour, shows the "version
available" banner with the changelog and "Update": in-place replacement
then "Restart now" (AppImage, Linux binary, standalone Windows exe, macOS
bundle), or download of the setup and "Install now" (installed Windows).
Clients older than beta9 (AppImage), beta12 (standalone Linux), beta14
(Windows) and beta15 (macOS) can only download: one last manual
installation for them. The setting for the depot that is queried is
`client_url` in the preferences; if the depot moves again, publishing at
the old address a cfg whose `module` points to the new one is enough,
clients follow.
